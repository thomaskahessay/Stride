# Adaptive Training Plan Engine — Implementation Plan

## Context

Stride currently handles missed workouts only through manual skip/move buttons (`WorkoutAdjustmentService`). There's no intelligence — the app doesn't react when users fall behind, report high fatigue, or have messy workout spacing.

A separate PR branch (`claude/review-stride-status-cFxOD`) already implements a **Ready Check** feature with `ReadinessCheck` model, `ReadinessEngine` scoring, and full UI. That feature recommends but doesn't act — the user sees "Dial Back" but the plan doesn't change.

This implementation adds a `PlanAdaptationEngine` that consumes Ready Check data alongside missed-workout signals and **adjusts the plan** — behaving like a cautious coach that protects the runner from injury.

### Key Design Decisions
- **Remove move functionality** — engine handles plan structure; manual rearranging conflicts with the coaching rules
- **Keep skip with a "today guard"** — skip is a free toggle during the current day; only counts toward compliance after the day passes. This prevents premature adaptation if the user changes their mind
- **Readiness Check is the same-day trigger** — the only way to trigger same-day adaptation is via the Ready Check
- **Readiness adaptations are user-choice** — presented as "Follow coach advice" / "I've got this"; user has final say
- **Missed-workout and spacing adaptations auto-apply** — based on objective facts, applied automatically with undo available via banner or workout detail

### 6 Coaching Rules Encoded
1. Protect consistency over perfection — don't make up every missed run
2. Avoid sudden load spikes — cap progression when compliance is low
3. Separate hard efforts with recovery — no back-to-back hard days
4. Reduce intensity before frequency — downgrade before dropping
5. Use subjective feedback — consume ReadinessCheck before adapting upward
6. Acknowledge strength/mobility — substitute when downgrading hard runs

## Step 3: PlanAdaptationEngine Service

**New file: `Stride/Core/Services/PlanAdaptationEngine.swift`**

### Public API
```swift
final class PlanAdaptationEngine {
    /// Runs all evaluation passes and applies objective adaptations (missed/spacing).
    /// Returns records for both auto-applied and pending readiness adaptations.
    func evaluateAndAdapt(
        plan: TrainingPlan,
        profile: UserProfile,
        readinessChecks: [ReadinessCheck],
        context: ModelContext
    ) -> AdaptationResult

    /// Applies a readiness-based adaptation when user accepts the coach recommendation.
    func applyReadinessAdaptation(
        workout: WorkoutDay,
        recommendation: ReadinessRecommendation,
        context: ModelContext
    ) -> AdaptationRecord

    /// Reverts an adaptation, restoring original workout values.
    func revertAdaptation(
        record: AdaptationRecord,
        workout: WorkoutDay,
        context: ModelContext
    )
}

struct AdaptationResult {
    let autoApplied: [AdaptationRecord]     // missed + spacing — already applied
    let pendingReadiness: ReadinessRecommendation?  // needs user choice
}
```

### 5 Evaluation Passes (priority order)

**Pass 1 — Missed Workout Assessment** (Rules 1 & 2) — AUTO-APPLIED
- Count missed + past-skipped workouts in trailing 7 and 14 days
- **Today guard**: `isSkipped` workouts where `effectiveDate` is today are excluded from counts
- Calculate `complianceRate` = completed / (completed + missed + pastSkipped) over 14 days
- Thresholds:
  - 1 missed: no action (continue plan as-is)
  - 2 missed in same week: downgrade next hard session in remaining week → easy
  - 3+ missed in 7 days: hold progression for current + next week, downgrade all remaining hard sessions this week
  - Compliance < 50% over 14 days: hold progression for next 2 weeks
- "Hold progression" = cap upcoming weeks' distances at the most recent completed week's actual mileage

**Pass 2 — Load Spike Prevention** (Rule 2) — AUTO-APPLIED
- Compare upcoming week's planned mileage to max actual completed mileage from past 2 weeks
- If planned increase > 10%: reduce upcoming distances proportionally to hit 10% cap
- Long run guard: if next long run distance > 10% beyond longest completed run in last 30 days, cap it
- Preserve workout types — only reduce distances

**Pass 3 — Hard Effort Spacing** (Rule 3) — AUTO-APPLIED
- Scan upcoming 7 days for violations:
  - Two hard workouts (tempo, interval, long run) on consecutive days
  - Long run within 1 day of tempo/interval
- Resolution hierarchy: protect long run > tempo > interval
  - Downgrade the lesser session using downgrade table
- Recheck after downgrade to ensure no cascading violations

**Pass 4 — Readiness Integration** (Rule 5) — USER CHOICE
- Read today's `ReadinessCheck` (if exists and `wasAccepted == true`)
- Map recommendation to proposed adaptation:
  - `sendIt` → no change
  - `dialBack` → reduce today's distance by ~20%, keep workout type
  - `swapRecovery` → downgrade today's workout to recovery run
  - `restToday` → convert to strength/mobility day
- Return as `pendingReadiness` — not applied until user accepts
- Before restoring any previously held progression: require most recent readiness score >= 60

**Pass 5 — Strength/Mobility Substitution** (Rule 6) — AUTO-APPLIED (as part of other passes)
- When any pass downgrades a run fully to rest: substitute `strengthDay` instead
- Set coaching note with brief strength/mobility suggestion (10-15 min bodyweight routine)
- Not a standalone pass — integrated into downgrade logic

### Downgrade Table (pure function in engine)
| Original | Level 1 Downgrade | Level 2 Downgrade |
|----------|-------------------|-------------------|
| intervalRun | tempoRun (same dist, moderate effort) | easyRun |
| tempoRun | easyRun (same dist, easy effort) | recoveryRun |
| longRun | longRun at -15% distance | easyRun |
| easyRun | recoveryRun (-20% dist) | strengthDay |
| recoveryRun | strengthDay | restDay |

### Constraints
- Only modifies today and future WorkoutDays (never past)
- Never creates new WorkoutDay objects — only modifies existing ones
- All modifications tracked via `AdaptationRecord` persisted in SwiftData
- Stores original values in WorkoutDay's `original*` fields before first modification
- Runs at most once per calendar day (`lastAdaptationDate` guard)
- Skips evaluation if today's workout is already completed
- If workout already adapted, doesn't re-adapt (prevents cascading downgrades)

2. **Model migration**: All new fields have defaults — SwiftData lightweight migration handles it
3. **Scenario tests**:
   - Miss 1 workout → no adaptation
   - Miss 2 in a week → next hard session auto-downgraded, banner shows with "Got it" / "Undo"
   - Miss 3+ in 7 days → progression held + hard sessions downgraded
   - Ready Check `dialBack` → user sees "Follow advice" / "I've got this" choice
   - Ready Check `restToday` → strength/mobility substitution offered
   - User taps "I've got this" → original workout preserved
   - User taps "Follow advice" → workout adapted, adapted badge visible
   - Two hard days back-to-back → lesser auto-downgraded
   - Long run > 10% over recent max → distance capped
   - User skips today → no immediate adaptation; next day engine accounts for it
   - User unskips same day → skip never counted
   - User taps "Undo" on banner or "Restore Original" on detail → workout reverted
   - Move button no longer present in workout detail
4. **UI**: Adaptation banner on dashboard, adapted badge on workout detail, coach advice buttons on Ready Check result
